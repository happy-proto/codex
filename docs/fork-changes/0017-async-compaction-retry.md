# 后台压缩失败后的退避重试

## 动机

后台压缩使用历史版本、模型、压缩 hash 和认证所有者代次去重。普通历史追加不会
改变此键；如果一次失败也永久占用去重键，后续检查点就无法再发起后台请求，
即使服务端已恢复，也只能在达到上下文上限时执行前台压缩。

## 行为与入口

- [后台压缩状态机](../../codex-rs/core/src/session/async_compaction.rs) 在失败后保留
  去重键，并允许后续合适的检查点在退避结束后重新捕获当前历史、发起请求。
  连续失败按 1、2、4、8、16、32、60 秒退避，此后保持 60 秒；新去重键重置退避。
  不新增轮询或自动定时请求，SDK 自身的传输重试仍由原有配置控制。
- 进行中的请求和成功结果继续去重；失败结果的接收器仍按
  [0012](0012-async-compaction-closed-receiver.md) 清理，不再等待已关闭的接收器。
- 捕获历史、注册任务及更新重试状态仍持有会话锁；图片等异步请求准备在释放锁后执行，
  沿用上游任务登记令牌，确保准备阶段的请求仍受会话关闭流程管理。
- 每次实际启动递增请求序号。旧任务迟到失败时，不得覆盖更新请求的退避状态；
  仅比较去重键不足以区分模型切换后又切回等情况。
- 回合取消、会话关闭、异步压缩功能开关和上下文阈值检查保留原有约束。
  达到上下文上限后仍复用可用结果或前台回退，不等待退避后再启动后台请求。
- [生命周期日志](0016-async-compaction-diagnostics.md) 记录请求序号、重试次数、
  是否允许同键重试及退避时间，不记录对话正文。

## 验证与维护

[回归测试](../../codex-rs/core/src/session/async_compaction_tests.rs) 用本地 Responses
模拟服务验证同一历史在失败后能重试，覆盖单次失败、连续失败、退避上限、取消阻止
重试、成功结果继续去重，以及既有取消后的结果复用。等待后台任务结束后检查请求数，
避免仅观察尚未执行的异步任务。

[CI](../../.github/workflows/fork.yml) 同时运行这些单元测试和既有异步压缩集成场景。
隔离 app-server 可用固定的“第一次输出无效、下一次输出有效”响应序列，检查有效
摘要是否在达到上限前被采用。该验证针对客户端重试缺陷，不判定服务端首次失败原因。

上游同步时关注去重键、请求所有权与后台重试策略。保留进行中请求去重、失败退避、
旧任务隔离和关闭接收器清理；上游引入等价机制后应收敛到一套实现。
