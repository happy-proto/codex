# 整理 fork 提交历史

用于用户明确要求归并、拆分或重写 fork 历史的任务；日常修复不自动触发历史整理。
仓库通用约定见 [AGENTS.md](../../../../AGENTS.md)，提交与推送遵循当前任务授权。

## 固定范围与归组

先 fetch `origin main`，核对本地、远端和工作树，记录旧 head、远端期望 SHA、
`scripts/fork/upstream-tag`、解析后的基线 commit 以及旧 head 的 tree SHA。
确认记录的基线是待整理 head 的祖先；只处理 `基线..head`，不改写上游提交。
纯历史整理保留该基线，不因重排提交重新选择 alpha 或刷新第三方快照。
用户另行要求同步时，先完成同步，再以同步后的 tree 作为整理前对照。

按 `docs/fork-changes/README.md` 与实际净 diff 建立“改造点 → 原提交及文件/hunk”映射。
“一个改造一个提交”指同一改造的最终实现、修复、测试和维护记录归并为一个完整提交，
不是每个文件一提交，也不是把整套 fork squash 成一笔。
混合提交按 hunk 拆回所属改造；版本同步、快照刷新和补充回归分别归回其长期维护的改造点。
共享 workflow、锁文件、入口和索引按实际依赖归属拆分，不机械按路径分组。
独立的仓库维护或 skill 更新可单列一个目的明确的提交，无需为纯维护事项新增产品改造编号。

## 演练与内容保护

在仓库外保存归组清单，并为旧 head 建立可恢复的本地 ref；在临时 detached worktree 演练。
可用交互式 rebase 的 reorder/fixup/squash，或按映射重建提交；不要仅为了凑数量保留无关修改。
顺序按依赖确定，不强求编号递增；最终提交标题描述完整行为，不保留临时调试或 fixup 标题。
保留现有作者和适用的 trailers；新增提交按仓库交付规则创建。

重排导致的冲突以归组目的和对照 tree 为依据处理，不能整文件选择某侧而夹带后续改造。
特别核对共享 CI 步骤、CLI 入口迁移、锁文件版本与依赖、生成物及跨改造的测试注册。
锁文件冲突通过项目工具重建并审查，不手工替换版本号或顺带升级无关依赖。

## 验证与交付

纯历史整理的决定性检查是 tree 完全相同，例如：

```sh
git diff --exit-code <旧-head> <整理后-head>
git rev-parse <旧-head>^{tree} <整理后-head>^{tree}
git log --reverse --oneline <基线>..<整理后-head>
```

同时核对基线及记录未变、提交数与归组清单一致、无 merge 或 fixup 残留、每个提交的实际 diff
只承担一个改造目的；用 `range-diff` 辅助发现遗漏，但不以它替代 tree 一致性。
如本轮还授权修改文档或代码，先证明纯整理结果与旧 tree 相同，再追加独立提交，
最后核对旧 head 到最终 head 只包含这些已授权的新变化。不要用宽泛路径排除掩盖代码差异。

tree 一致时可沿用旧 tree 的内容验证证据，不为历史重排重复执行本地重型测试；
新增内容仍按其风险验证。旧 SHA 的 CI/Release 不能冒充新 SHA 的构建或发布结果。
更新本地 `main` 前再次核对工作树与旧 head；推送前 fetch 并核对远端未变化，
使用记录的精确旧 SHA 执行 `--force-with-lease=refs/heads/main:<远端旧-SHA>`。
lease 失败时停止推送，读取并整合远端新提交，不放宽为无条件强推。

回读远端 SHA、默认分支和新 head 的 CI/Release 状态，按 [release.md](release.md) 区分各层验收。
清理临时 worktree；旧历史备份 ref 保留到远端核验完成，若继续保留供恢复，在交付中说明位置。
最终报告整理前后提交数、归组结果、tree 对照、新增变化、备份及最新 CI/Release 状态。
